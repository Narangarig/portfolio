---
title: Ship the narrow version first
date: 2026-06-14
excerpt: A smaller thing that's finished beats a bigger thing that's almost there — most of what I build starts by cutting scope, not adding it.
---
The easiest way to stall a small project is to keep it in "almost ready" for months. The fix I keep coming back to is boring: cut scope until what's left fits in a weekend, ship that, and let the next version earn its own weekend.

## What "narrow" usually means in practice

- One user flow, not five. Pick the one that proves the idea.
- One content type, hard-coded if needed, before building a system to manage many.
- Static and simple hosting before reaching for a database or a backend.

None of this is a permanent ceiling — it's a sequencing choice. The system that supports five content types can still get built later, once the one-content-type version has told you whether anyone wants it.

## A small test

Before adding a feature, I ask whether cutting it would stop the project from being useful at all. If the answer is no, it goes on the list for *after* the first version ships, not into it.
